# 桌面整理：视频动态壁纸实施方案

> 日期：2026-11-26　范围：`extensions/desktop`（`pulse.desktop` 桌面整理插件）　状态：待确认（§11 有 4 个需要拍板的问题）
>
> 目标：用户选一个视频当壁纸。**不限制视频分辨率**，但播放时的内存要尽量小。画质、帧率不打折。
> 依据：原型 `extensions/desktop/tests/video_wallpaper_probe.cpp` 的实测数据，记录在 `bench_data/video-wallpaper-proto/RESULTS.md`
> （测试机：GTX 1060 3GB，3840×2160 屏）。下文出现的数字都来自这台机器，没有在其他机器上验证过。

---

## 0. 一页结论

| 决策 | 结论 | 依据 |
|---|---|---|
| 播放管线 | **自建**：SourceReader 硬件解码（D3D11VA）→ `ID3D11VideoProcessor` 一次缩放 → **双缓冲交换链，尺寸不超过屏幕** → DComp | 1080p 视频在 4K 屏上：自建 56 MB 显存，Media Engine 484 MB |
| 不用 Media Engine | 窗口无交换链模式会按屏幕尺寸保留多份 RGB 缓冲，暂停也不释放 | 实测 4K 屏上 484–839 MB |
| 不用 FFmpeg 解码 | d3d11va 按 16 帧参考帧预留缓冲 | HEVC 4K 462 MB，Media Foundation 233 MB |
| 不自写解码前端 | 自写的 HEVC DXVA 前端输出与系统解码器逐位一致，但在 NVIDIA 上只省 5–25 MB：每个解码器约 86 MB 是驱动固定开销 | `hevc_dxva.cpp` 原型 |
| 不限分辨率的办法 | 视频**大于屏幕，或显卡解不了**，就后台**转码到屏幕分辨率**一次，结果缓存起来 | 8K→4K 播放 520→133 MB；8K→1440p 64 MB；亮度 PSNR 42.7–47 dB |
| 转码管线 | 只用 Media Foundation：硬件解码 → VideoProcessor 缩放 → Sink Writer + 硬件编码器（HEVC，10-bit 保持 Main10；没有 HEVC 编码器时用 H.264） | NVIDIA HEVC Encoder MFT：8K→4K 1.5 倍实时，4K→1440p 6.4 倍 |
| 暂停 | 暂停超过 30 秒就**释放解码器和交换链**，只保留一张最后一帧 | 暂停本身不释放内存；重开首帧 18–41 ms |
| 放在哪 | 作为**层窗口自己合成树的最底层**可视对象（玻璃层之下）。不碰 Explorer 的 WorkerW / Progman | 层窗口铺满虚拟屏、接管图标后，桌面上能看到的东西都由我们画 |
| 玻璃取样 | 直接拿视频帧缩一张 1/4 分辨率的纹理喂给液态玻璃，不走 WGC 截屏 | 帧本来就在 GPU 上 |
| 进程 | 播放放在宿主进程内的专用线程，用独立的 D3D 设备；转码放在**独立进程**，用作业对象限制内存 | 软解 8K H.264 转码峰值 2.6 GB，不能放进宿主 |

预计常驻开销（4K 屏，播放已转码的 4K 视频）：宿主进程显存约 **+133 MB**，DWM 约 +80–127 MB（4K 交换链参与合成时的实测；DWM 自身基线有 ±50 MB 波动）。
1440p 屏：约 **+64 MB**。长时间暂停后：一张最后一帧（4K 33 MB，1440p 15 MB）。

## 1. 范围

**做：**
- 壁纸可以是一个视频文件：MP4 / MOV / MKV 容器，H.264 / HEVC（8/10-bit SDR）/ VP9 / AV1。实际能播哪些，取决于本机 Media Foundation 装了哪些解码器。
- 循环播放，永远静音，不创建音频渲染器。
- 填充方式：铺满（裁切）/ 适应（留黑边）。
- 遵循现有的"全屏或节能时暂停"开关，另外在锁屏、熄屏、桌面被完全挡住时暂停。
- 视频大于屏幕或显卡解不了时，后台转码到屏幕分辨率，缓存结果，原文件不动。
- 液态玻璃折射视频画面。

**不做（本期）：**
- HDR 视频（PQ / HLG / BT.2020）：识别出来后直接告诉用户暂不支持，不偷偷转成 SDR。
- 声音、播放列表、按时间切换、网页或程序类壁纸（这些是 Wallpaper Engine / Lively 的领域；它们继续由现有的 `LiveWallpaperDetector` + WGC 路线支持）。
- 不接管图标时的视频壁纸（见 §11 Q1）。
- 自写解码前端（§0 已说明）。

## 2. 架构

```
pulse_desktop_host.exe
 ├─ DesktopRenderer（UI 线程）        层窗口合成树：
 │                                    root ─┬─ video_visual   ← 新增，最底层
 │                                          ├─ glass_visual
 │                                          └─ dcomp_visual（现有的透明主交换链）
 ├─ VideoWallpaperPlayer（播放线程）   独立 D3D11 设备 + VideoProcessor + 交换链（内容挂在 video_visual 上）
 │                                    每 N 帧向渲染器交一张 1/4 分辨率的玻璃取样纹理（共享 NT 句柄 + keyed mutex）
 └─ WallpaperPolicy（UI 线程）         看视频信息 + 显卡能力 + 屏幕尺寸 → 决定直接播放、转码还是拒绝

pulse_wallpaper_transcoder.exe（按需启动，作业对象：内存上限、低优先级、随宿主退出而终止）
     SourceReader → VideoProcessor → Sink Writer(硬件编码器) → %LOCALAPPDATA%\Pulse\wallpaper-cache\<key>.mp4
```

### 2.1 为什么放在层窗口里，而不是 Explorer 的壁纸窗口里

层窗口是一个顶层工具窗口，始终紧贴在 Explorer 的桌面宿主之上，铺满虚拟屏（`desktop_mount.cpp`）。接管图标后，桌面上能看到的东西都由我们画。把视频放在它的合成树最底层：

- **z 序永远正确**，不用处理经典 WorkerW 和 24H2 Progman 两套层级的拆分时机。
- **玻璃直接取帧**：现有动态壁纸路线（WGC 截取 Explorer 的壁纸窗口）是为别人的窗口设计的，用在自己的视频上纯属浪费。
- **主交换链已经是预乘透明**（`desktop_renderer.cpp`，`DXGI_ALPHA_MODE_PREMULTIPLIED`，每帧清成透明），视频从下面透出来，不用重画主层。

**代价**：如果用户关掉"接管图标"，Explorer 的原生图标在层窗口下面，会被视频盖住。本期的做法是：只有接管图标时才提供视频壁纸（§11 Q1）。

### 2.2 为什么播放用独立的 D3D 设备

- 解码和渲染器不抢同一个立即上下文。渲染器的玻璃 / 文字绘制不会被 VideoProcessor 卡住，反过来也一样。
- 播放出问题时，可以整个丢掉这台设备和线程再重建，渲染器不受影响。
- 同一块显卡上，不同设备创建的交换链应该可以挂进同一棵 DComp 树。**原型没有验证过这一点，列为 P1 的第一步**；如果不行，就改为播放线程用渲染器的设备，同时开启多线程保护。玻璃取样纹理通过共享句柄交给渲染器，每张约 2 MB（4K 的 1/4）。

### 2.3 为什么转码放在独立进程

- 软件解码 8K H.264 转码时峰值 2.6 GB。一旦放进宿主，宿主被系统杀掉或崩溃会触发重启熔断：连续三次重启后，"桌面整理"会被自动关掉。
- 沿用 Pulse 现有的外部工具约束（`src/common/ffmpeg_tool.h`：kill-on-close 作业对象、内存上限、只继承标准句柄），但工具换成我们自己的 `pulse_wallpaper_transcoder.exe`，不依赖 FFmpeg。

## 3. 播放管线（VideoWallpaperPlayer）

### 3.1 打开

1. `MFCreateSourceReaderFromURL`：设置 `MF_SOURCE_READER_D3D_MANAGER`（播放线程自己的设备）和 `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`；取消所有流，只选第一个视频流（没有音频渲染器）。
2. 输出类型先试 P010 再试 NV12（10-bit 来源不降精度），CPU 上不做任何转换。
3. 读 `MF_MT_MINIMUM_DISPLAY_APERTURE` 拿到裁切后的有效区域；读 `MF_MT_YUV_MATRIX` / `MF_MT_VIDEO_NOMINAL_RANGE` 设置 VideoProcessor 的输入色彩空间（原型固定按 BT.709 处理，BT.601 的片子会有轻微色偏，这次要改掉）。
4. 首帧解码出来之前，`video_visual` 先显示缓存的海报图（§5.3），避免切换时黑一下。

### 3.2 每帧

- 解码出的 NV12/P010 表面 → `VideoProcessorBlt` → 交换链后台缓冲 → `Present`。
- **交换链尺寸 = min(视频有效尺寸, 屏幕尺寸)**，保持比例。DComp 用变换缩放到"铺满 / 适应"，插值用线性。
- **格式**：先试 NV12 组合交换链（需要硬件支持 YUV 叠加层），失败就用 BGRA。测试机（NVIDIA）`CheckOverlaySupport` 返回 0，只能用 BGRA；Intel 核显上可能可以用 NV12，能再省一半交换链内存（4K 时 63 MB → 25 MB），待验证。
- **出帧节奏**：用可等待交换链（`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`，最大延迟 1），按样本时间戳对照 QPC 时钟出帧，落后超过两帧就丢一帧追上。原型用 Sleep 轮询，只适合测内存，不能照搬。
- **循环**：读到流结尾后跳回 0，时间戳接着上一轮的末尾往下算，衔接处不出现空档（原型已验证）。

### 3.3 暂停和释放

| 事件 | 动作 |
|---|---|
| `ShouldPauseLiveActivity(pause_on_fullscreen_or_battery)` 为真（全屏或演示模式、节能模式、低电量） | 暂停 |
| 锁屏（`WM_WTSSESSION_CHANGE`，已有） | 暂停 |
| 熄屏（新注册 `GUID_CONSOLE_DISPLAY_STATE`） | 暂停 |
| 桌面被完全挡住（前台窗口最大化且铺满视频所在的显示器；新增判定） | 暂停 |
| 暂停超过 30 秒 | **释放**：先把最后一帧拷进一张 DComp 表面（4K 33 MB，1440p 15 MB），再释放 SourceReader、解码器、VideoProcessor 和交换链 |
| 恢复 | 重开 → 跳到暂停时的位置 → 首帧出来后换回交换链（实测重开首帧 18–41 ms） |

原型发现：Media Engine 在熄屏时会自动停止出帧，自建管线不会，它按自己的时钟照常解码。所以熄屏暂停必须自己做。

### 3.4 玻璃取样

- 每次出帧后（频率跟随现有的"动态折射帧率"设置：静态 / 30 / 60），VideoProcessor 再缩一张 1/4 分辨率的 BGRA 纹理，写进与渲染器共享的纹理（keyed mutex），然后通知 UI 线程。
- 渲染器把它当作现有 `LiveWallpaperSource` 的清晰帧和磨砂帧来源，复用已有的模糊和取样代码。"静态"档只在暂停或换视频时更新一次。

## 4. 什么时候转码（WallpaperPolicy）

用户选定视频后先探测一次（SourceReader 只读媒体类型，不解码）：编码、尺寸、位深、帧率、HDR 标记、`MF_PD_DURATION`。显卡能力用 `ID3D11VideoDevice::CheckVideoDecoderFormat` + `GetVideoDecoderConfigCount`（按视频尺寸）判断；这是否足够判断"能否硬解"，还需要真机验证，否则就试开解码器读第一帧。

| 情况 | 决定 |
|---|---|
| 能硬解，尺寸 ≤ 目标尺寸 × 1.1 | **直接播放原片** |
| 能硬解，尺寸 > 目标尺寸 × 1.1 | **转码**到目标尺寸；转码期间先播原片，原片预计显存超过预算（§11 Q3）就只显示海报图，转好后切过去 |
| 不能硬解（如 1060 上的 8K H.264、没有硬解的 AV1） | **转码**（软件解码，在独立进程里，受作业对象内存上限约束）；转码期间只显示海报图 |
| 本机没有这种编码的解码器（如没装 HEVC 视频扩展） | 无法转码，提示"这台电脑缺少 HEVC 视频扩展，可以在 Microsoft Store 免费安装"之类的大白话 |
| HDR | 提示暂不支持 |
| 软解转码超出内存上限 | 提示"这个视频太大，这台电脑转换不了"，壁纸保持原样 |

- **目标尺寸** = 视频会覆盖的最大那台显示器的原生分辨率（物理像素，与 DPI 缩放无关）。显示器配置变了以后，下次播放时重新判断。
- **转码输出**：硬件 HEVC 编码器（10-bit 来源用 Main10）→ 没有就用硬件 H.264 → 再没有就用系统的软件 H.264 编码器（慢；低优先级）。如果本机能编码 HEVC 却不能解码 HEVC，就改用 H.264 输出。
- **码率**：0.10 bit/像素/帧（4K30 约 25 Mbps，1440p30 约 11 Mbps）。实测亮度 PSNR 42.7–47 dB，SSIM 0.97–0.995。
- **顺带的好处**：NVIDIA 编码器输出的码流只用 2 帧参考帧、没有 B 帧，播放时比原片更省（8K→4K 的结果播放只要 133 MB，而 x265 编码的 4K 原片要 233 MB）。"不超过屏幕、但参考帧很多的视频也重新编码"本期不默认开启（§11 Q4）。

## 5. 转码器与缓存

### 5.1 `pulse_wallpaper_transcoder.exe`

- 参数：源文件路径、输出路径（临时文件名）、目标尺寸、编码偏好；通过宿主的命名管道回报进度（每秒一次：已处理时长 / 总时长）。
- 作业对象：`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；`JobMemoryLimit` = min(3 GB, 可用物理内存的 50%)；`BELOW_NORMAL_PRIORITY_CLASS`；I/O 优先级设为低。
- 暂停条件与播放一致（全屏或节能时），避免和游戏、视频会议抢 GPU 编码器。
- 写完先 `Finalize`，再原子重命名为正式缓存文件。进程被杀、失败或取消时，只会留下临时文件，下次启动时清理掉。

### 5.2 缓存

- 位置：`%LOCALAPPDATA%\Pulse\wallpaper-cache\`。
- 键：SHA-256(源文件完整路径 + 大小 + 修改时间 + 目标宽高 + 编码偏好 + 方案版本号)。
- 上限默认 2 GB，按最近使用淘汰；当前壁纸的条目不淘汰。
- 源文件被移动、删除或修改后：海报图仍然能显示，同时提示用户重新选择。

### 5.3 海报图

第一次探测时解出第一帧，按目标尺寸存成 JPEG（4K 约 1–2 MB），用于首帧前、转码中、释放后的显示。

## 6. 设置与存储

### 6.1 入口

用户想换视频壁纸，真实的路径有三条。都落到同一个宿主动作 `set-video-wallpaper <path>`：

| 场景 | 入口 | 依据 |
|---|---|---|
| 在 Pulse 里刚找到 / 下载了一个视频 | **右键视频文件 → "设为桌面壁纸"**（命令组"桌面整理"） | SDK 已支持按扩展名过滤的文件命令（`PULSE_COMMAND_FILES` + `extensions`，最多 32 个扩展名，选中 1 个时显示），插件在 `RegisterStaticCommands` 里多注册一条即可 |
| 在桌面上调外观 | 桌面右键 → **美化桌面**抽屉 → 壁纸页 → "视频"一栏（§6.2） | 现有入口 |
| 手边就有这个文件 | 把视频文件**拖进美化桌面抽屉的壁纸预览** | 抽屉已经是放置目标（OLE 拖放基础设施现成） |

插件设置页（"外观与场景"）也加同样的项，供不习惯右键的用户使用：壁纸（系统 / 视频）、视频文件 + "选择视频…"、填充方式、状态行。

### 6.2 美化桌面抽屉重做

现状（`DrawBeautifyDrawer`，宽 372 DIP）：一个长滚动列表，从上到下依次是壁纸 5 张缩略图、强调色、窗口效果、玻璃风格、动态折射、图标文字、图标大小、程序坞 4 项、双击隐藏、小组件。问题：
- 没有地方放视频；"系统"那张缩略图只是一个显示器图标，看不出现在的壁纸是什么。
- 要调程序坞或小组件得一路往下滚；壁纸、效果、图标、程序坞四类东西混在一起。

**改为：标题下一排分页 "壁纸 · 效果 · 桌面 · 程序坞"**。每页一屏放得下，不用滚动。原有设置项一项不少，只是挪到对应的页里：

| 页 | 内容 |
|---|---|
| **壁纸** | 当前壁纸大预览（16:9）→ "图片"一排（系统 = **真实的当前 Windows 壁纸缩略图**、蓝、暮色、森林、照片）→ "视频"一排（最近用过的最多 3 个 + "选择视频…"）→ 选中视频时出现：文件信息、状态行、填充方式（铺满 / 适应）→ 强调色跟随壁纸 |
| **效果** | 窗口效果、液态玻璃风格、动态折射（后两项仅在选液态玻璃时出现，同现状） |
| **桌面** | 图标文字、图标大小、双击空白处隐藏图标、小组件（天气 / 日历 / 待办 + 全部小组件…） |
| **程序坞** | 显示液态玻璃程序坞、位置、收回方式、窗口收回效果、系统状态与托盘区 |

外观按 2026-11-26 定下的 macOS 规范：抽屉圆角 22、液态玻璃材质、分页用胶囊分段控件、按钮用胶囊形。
抽屉记住上次打开的分页；从右键"设为桌面壁纸"或拖放打开时，直接停在壁纸页。

**壁纸页的视频状态**（预览上的胶囊标记和下方状态行）：

| 状态 | 预览 | 状态行 / 操作 |
|---|---|---|
| 播放中（原片已适合屏幕） | 海报 / 实时画面，左上角"视频"胶囊，右下角"暂停"按钮 | `3840×2160 · 0:45 · 正在播放` |
| 播放中（已优化） | 同上 | `已为这块屏幕优化（原片 7680×4320）` |
| 正在优化 | 海报 + 进度条 | `正在为这块屏幕优化… 42%`　[取消] |
| 已暂停（自动） | 海报，暗角 + "已暂停" | `全屏程序运行中，已自动暂停` / `节能模式，已自动暂停` |
| 缺少解码扩展 | 海报（若能取到）或占位 | `需要 HEVC 视频扩展才能播放这个视频`　[去 Microsoft Store] |
| 文件不见了 | 上次的海报 | `找不到这个视频，可能已移动或删除`　[重新选择] |
| 太大 / HDR | 海报 | `这个视频太大，这台电脑转换不了` / `暂不支持 HDR 视频` |
| 未接管图标（§11 Q1） | — | `视频壁纸需要由桌面整理显示图标`　[开启] |
| 拖放悬停 | 预览变成放置区 | `松开即设为壁纸` |

文字要求：用户能看懂的大白话，不出现"DPB""MFT""转码"这类词（界面上说"优化"）。插件按本地约定直接写中文字符串；以后如果有文字要进 Pulse 主程序，按 AGENTS.md 走 `tools/l10n/catalog.tsv`。

效果图：`docs/design/video_wallpaper_beautify.html`（浅色 / 深色，以上全部状态，含 Pulse 右键入口）。

### 6.3 存储

- 插件持久化值有 **1024 字节上限**（`DesktopPrefs` 打包成一个字符串）。视频路径可能很长，**不能放进这个值**。
- `DesktopPrefs` 里只加两个小字段：`wallpaper_kind`（0 系统 / 1 视频）、`video_fill`（0 铺满 / 1 适应）。
- 视频路径和缓存键写进宿主自己的状态文件（与 `undo_history.cpp` 写的桌面状态同一处，新增 `video_wallpaper` 对象）。插件通过已有的 IPC 读状态显示文件名。

## 8. 内存预算（验收标准）

在 GTX 1060 + 4K 屏上测得，作为回归门槛。其他机器要重新标定：

| 场景 | 宿主显存增量 | 宿主工作集 |
|---|---|---|
| 1080p 原片（H.264） | ≤ 70 MB | ≤ 90 MB |
| 4K 屏 + 已转码的 4K 视频 | ≤ 150 MB | ≤ 110 MB |
| 1440p 屏 + 已转码的 1440p 视频 | ≤ 75 MB | ≤ 90 MB |
| 长时间暂停后 | ≤ 一张最后一帧 + 10 MB | — |
| 转码进程（硬件解码） | 峰值 ≤ 900 MB 显存 | ≤ 450 MB |

DWM 的开销单独记录（PDH `GPU Process Memory`），不计入门槛，但每次都要报告。

按 AGENTS.md 的范围原则：只构建桌面扩展相关的目标，只跑与改动相关的测试。

- **单元测试**（新建 `pulse_desktop_video_wallpaper_test`，沿用 `[PASS]/[FAIL]` 格式）：
  - 策略决策表（§4 每一行，包括 ×1.1 阈值）；
  - 缓存键（路径或修改时间变化后应该失效）和淘汰规则；
  - 暂停状态机（事件序列 → 暂停 / 释放 / 恢复）；
  - 状态文件读写，以及插件持久化值不超过 1024 字节（扩展现有的 `pulse_desktop_settings_test`）。
- **集成测试**：把原型探针改造成 `pulse_desktop_video_wallpaper_bench`，对 `bench_data/` 下生成的测试片跑播放和转码，按 §8 的门槛判定 PASS/FAIL，并输出 CSV。
- **正确性**：
  - 转码结果整段 PSNR/SSIM ≥ 40 dB / 0.97（开发机上用 FFmpeg 核对，Pulse 运行时不依赖 FFmpeg）；

- **真机**：开发版插件在隔离的测试配置下运行，不影响用户正在用的桌面。测完卸载，恢复原壁纸。

## 12. 风险

- **驱动差异**：NVIDIA 每个解码器约 86 MB 的固定开销，以及"创建方式不同、开销不同"的现象（同一个文件，MF 解码 133 MB，自写前端 185 MB），在 Intel / AMD 上是什么情况未知。§8 的门槛要在这两家的显卡上重新标定。
- **DWM 开销**：4K 交换链参与合成时，DWM 显存多出约 80–127 MB，不在我们的进程里，但用户会算到"开了动态壁纸更占内存"上。NV12 交换链（如果支持）是唯一的缓解办法。
- **编码器会话数**：消费级 NVIDIA 显卡同时可用的编码会话有限。转码时如果正好在录屏或开视频会议，可能失败，需要重试并退回 H.264 或软件编码。
- **HEVC 解码依赖商店扩展**：Windows 默认不一定带 HEVC 解码，需要按 §4 处理。
- **长视频**：转码时间与时长成正比（8K→4K 是 1.5 倍实时：10 分钟的视频要约 7 分钟）。需要进度显示、能取消、能断点续做（P2 末尾评估）。
- **原型局限**：测试片是合成画面，每段只有 10 秒；还没在真实拍摄素材、核显和多屏上测过。
