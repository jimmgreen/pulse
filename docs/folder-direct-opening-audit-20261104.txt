Folder direct opening audit -- 2026-11-04

Evidence
User confirmed a normal desktop folder. Supplied 111111 runtime session
app-48364 records integration=1, takeover=1, compat=1. Seven handoffs are
observer-originated (external_open entry=1), with native candidates already
875-1125 ms old when accepted. Candidate age is not a measured visible time.
The previous SettingsController policy explicitly disabled folder registration
when compatibility was selected. This explains why observer handoffs occurred.

Changes
Folder registration now depends on the master and folder selections only.
Compatibility supplements, rather than disables, the direct verb. Startup
upgrades enabled old compatibility configurations through ApplyFolderOpen,
preserving explicit disabled selections and the existing registry backup.
UI status requires actual folder registration. Migration failures are error
events. explorer_takeover_config includes folders_requested,
folders_direct_desired and folders_direct_active, including changes in its
event suppression key. Compatibility descriptions now explain fallback scope.

Other paths audited
- Settings actions for other scopes and repair use the same direct policy.
- Settings import excludes machine-local integration choices.
- RestoreOthers disables integration only for explicit restore-system action.
- Normal uninstall restores associations; upgrade uninstall skips restoration.
- Legacy residue repair requires absent commands and absent backups; it does
  not remove a valid owned folder command.
- Launcher native fallback occurs only before a host is successfully created;
  no registry removal and no post-launch timeout fallback.
- Win+E native fallback follows cancelled delivery, not successful dispatch.
- ApplyDefaultFileManager forwards its explicit requested on/off value.

Remaining findings / limits
The separately identified directory-move failure gap is now addressed:
new files are committed before association migration, owned commands are
verified at the new location, and only then does the current uninstall engine
remove the old installation in upgrade mode. Partial migration failures retain
both executable locations and return an installation failure. Startup and
shared runtime registration follow old-install cleanup.
Explicit Explorer/COM callers that bypass default verbs remain observer
coverage; direct registration alone cannot prove they never show Explorer.
No measured 99 percent coverage claim is made.
The previous extension build blocker has been removed from the production
configuration by its owning work. A newly added reactive probe source required
CMake regeneration before the main executable linked successfully. Production
payload targets and setup then built successfully. Release rebuild and installer verification
are recorded separately in bench_data/folder-direct-release-build.log and
bench_data/folder-direct-installer-verification.json. No installed-app desktop
double-click result is claimed: the user requested the installer to test it.
