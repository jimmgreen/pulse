# Pulse 增强包开放能力与 AI 协同实施方案

日期：2026 年 11 月 2 日  
适用对象：Pulse 主程序、增强包、AI 与文件操作模块开发者  
范围：架构与实施计划，不包含本轮代码修改、构建或上线

## 1 建议先做什么

**建议把 Pulse 已有动作、文件操作与 AI 工具收敛到同一个受控能力层，先开放声明式工作流增强包，再开放经过隔离验证的脚本包。不要把现有内部函数、菜单命令或官方 AI 管道直接开放给任意进程。**

第一版的完成标准不是“所有功能都能调用”，而是两个增强包可以通过公开协议完成实际任务：

- **归档整理包**：读取用户选定目录的元数据，按确定规则或 AI 建议生成移动计划，经用户确认执行；可查看逐项结果并撤销属于自己的操作。
- **批量重命名包**：输入模板或自然语言，生成旧名到新名的对照表，检查重名与非法名称，确认后走现有重命名引擎。

MVP 不开放任意 Shell、外部程序启动、永久删除、全盘扫描、任意脚本、原生 DLL 注入、任意网页面板，也不建设市场、支付或自动发布系统。公开 API 随实际场景逐步增长。

## 2 已有基础和真正缺口

以下“已有”指本次检查到的源码结构，不代表做过本机 Windows 运行验证。表中的新能力与后文示例均为**拟议设计**。

| 领域 | 已有实现与源码定位 | 开放平台仍需补齐 |
| --- | --- | --- |
| 动作目录 | `app/actions/action_inventory.h` 有稳定动作 ID、风险类型及菜单与快捷键映射；`action_registry.h` 提供动作视图和执行入口 | 建立公开白名单、稳定参数与结果 Schema；不能公开仅在一次构建内稳定的 `index` 或菜单整数 |
| 动作策略 | `action_policy.h/.cpp` 的 `AiPolicy` 区分 `Direct`、`Confirm`、`Plan`、`Locked` | 增加插件身份、用户授予、资源范围与调用链判断；`Direct` 不能理解为任意插件天然获准 |
| 文件计划 | `action_files.h` 有 `PlanFileOp`、`SubmitFilePlan`、文件行与目标目录等结构 | 从当前窗口状态解耦；固定选择快照、生成不可变计划及确认凭据，并重新验证执行目标 |
| 操作引擎 | `ops/ops_manager.h` 有任务、取消、冲突、部分失败、撤销组、回收站拒绝等结构 | 对公开调用增加来源归属、任务查询、授权与幂等关联；不另建一套文件操作引擎 |
| AI 工具 | `ai_tools.h/.cpp` 注册九类现有工具，见下文 | 统一适配能力层；工具发现按授权过滤，避免维护独立的插件权限实现 |
| AI Broker | `ai_broker.h` 有并发、取消、超时、确认、事件与日志；默认最多 4 个连接，每连接 4 个调用 | 新增公开平台身份与配额语义；原有连接上限不是完整资源隔离 |
| 内部协议 | `ipc/ai_tool_protocol.h` 为长度前缀 UTF-8 JSON，最大帧 4 MiB；同构建与固定 SHA 保证兼容，不做版本协商 | 第三方包版本独立，需要公开 API 协商、结构限制与特性探测 |
| 官方增强包 | `pack_catalog.h` 固定文件大小与 SHA-256；`pack_installer.h` 有临时目录、完整校验、原子切换与已安装文件复用 | 独立的第三方清单、发布者身份、升级权限差异、撤销与兼容策略 |
| 官方 AI 连接身份 | `ai_pack.h/.cpp` 验证官方 AI 宿主路径、文件身份、会话与用户，`ai_service.cpp` 将其用于 peer 校验 | 保留原验证，另设计可信插件宿主到核心的入口；不能删除验证来“支持插件” |

现有 AI 工具包括 `pulse.get_context`、`pulse.list_folder`、`pulse.search`、`pulse.get_properties`、`pulse.reveal`、`pulse.create_zip`、`pulse.undo_last`、`pulse.find_actions` 与 `pulse.run_actions`。它们说明复用入口已存在，但并不等于安全的第三方 SDK 已经完成。

两个迁移细节需要特别注意：

1. `ai_settings.h` 当前内置助手默认启用，MCP 默认关闭；MCP 开启后的默认动作组包含 `view` 和 `create`，不是“默认只读”。既有设置不应因平台迁移被悄悄扩大或重置。
2. 当前 `ClientRecord` 与 `AllowRule` 使用 hello 中的客户端名称，撤销记录也以“AI 操作”总体归类。名称不能作为第三方身份凭据，“AI 做的”也不能证明“由这个插件做的”。

## 3 目标结构

```text
用户操作                     内置助手与现有 MCP
    │                              │
    ├──── 内部适配器 ───────────────┤
    │                              │
声明式增强包 → WorkflowRunner      │
隔离脚本包   → ExtensionHost ───────┤
                                   ▼
                        CapabilityService
         身份 → Schema → 权限与资源 → 预检 → 确认 → 执行
                                   │
              ┌────────────────────┼───────────────────┐
              ▼                    ▼                   ▼
        现有动作适配器        索引与内容适配器      文件计划适配器
              │                    │                   │
           UI 线程              现有服务             OpsManager
              └────────────────────┴───────────────────┘
                   统一任务状态 审计 归属 撤销
```

`CapabilityService` 是拟新增的**策略和协议边界**，不是把所有功能重写为服务。内部每项能力通过 Adapter 调用现有代码；UI 相关部分只将短任务投递到 UI 线程，搜索、扫描、压缩与模型请求不得阻塞 UI。

公开接口使用稳定、类型化、语义化的 ID，例如 `context.selection.read`、`files.planRename`。它们不一定与现有动作 ID 一一对应；适配表可以映射到 `file.rename` 等现有动作。禁止通过模拟快捷键、发送菜单命令或让插件拿到 `AppState*` 来达成功能。

## 4 第一批公开能力

下表所有公开名称均为拟议 API，不是当前可直接调用的接口。第一版只发布能够给出稳定语义、完成授权与测试的子集。

| 能力 | 最小数据或效果 | 首批范围和限制 | 复用位置 |
| --- | --- | --- | --- |
| `context.selection.read` | 选中项引用、当前目录引用、快照版本 | 用户触发时读取，不默认暴露全部窗口、历史或其他标签页 | `ai_tools_ui.*`、动作状态 |
| `files.list`、`files.stat` | 分页条目、基础元数据 | 限已授予目录；不读取文件正文；分页与数量上限 | `ai_tools_fs.*` |
| `search.query` | 授权范围内匹配项 | 宿主约束查询范围并过滤返回值；不先返回全盘结果再由插件过滤 | `ai_tools.cpp`、索引客户端 |
| `ui.reveal` | 在 Pulse 展示已获准项目 | 不等同于执行程序或打开任意协议 | `pulse.reveal` 适配 |
| `archive.create` | 创建新归档与任务 ID | 仅授权输入和输出目录；禁止静默覆盖；沿用现有压缩与撤销逻辑 | `PlanZip`、`RunZip` |
| `files.planMove`、`files.planRename` | 不可变计划、冲突与风险摘要 | 不产生文件变更；只支持本地文件的首批场景 | `PlanFileOp` 及批量重命名相关引擎 |
| `operations.commit` | 执行已确认计划 | 核心确认凭据绑定计划、调用者与目标；不能由插件声明“用户已确认” | `SubmitFilePlan`、`OpsManager` |
| `operations.get/cancel/undo` | 自有任务状态、取消或撤销请求 | 只能处理本人任务；撤销仍受最新栈状态、对象变化与可撤销性约束 | `OpsManager`、新归属索引 |
| `ui.showResult`、`settings.own` | 声明式结果、插件自有设置 | 宿主控件；设置按插件命名空间隔离 | 新声明式 UI 适配层 |
| `ai.propose` | 受 Schema 约束的结构化建议 | 用户选择的模型连接；独立的数据外发授权与调用预算 | 现有助手与模型连接适配 |

标签、收藏、内容抽取、比较、托盘等可以成为第二批。`settings.set` 不宜直接对第三方开放：现有 AI 策略有专门处理，公开接口应按设置项白名单重新分类。永久删除、回收站清空、驱动器操作、系统设置、程序启动与 Shell verb 首版均不开放。将来即使开放，也不能用插件安装时的一次同意取代每次危险操作确认。

## 5 身份和权限必须由宿主决定

### 5.1 三类增强包

- **声明式工作流包，第一阶段**：JSON 清单与宿主定义的有界 DAG 步骤，只允许白名单参数和过滤条件；无任意表达式引擎、循环、代码或网络。限制步骤数、输入规模与总成本，拒绝环和未定义步骤。
- **隔离脚本包，后续阶段**：TypeScript 编译为 JavaScript，运行在独立 ExtensionHost；只使用显式 host ABI。先完成 Windows 隔离 PoC 和攻击测试，再决定是否允许第三方分发。
- **受信任原生包，独立信任级别**：保留官方原生增强包路线。原生可执行文件若以用户普通权限运行，拥有的权限可能远超 API 白名单，因此必须显著告知其信任性质，不能伪装成“受限插件”。

独立进程和 Job Object 可以帮助故障隔离、退出清理与资源控制，**本身不是安全沙箱**。删除 `require`、隐藏几个 JS 全局变量也不能保证隔离。强隔离路线应验证 AppContainer、网络能力与对象 ACL、宿主 IPC、可访问文件及子进程行为；无法满足边界就继续只开放声明式包。AppContainer 方案需在实际支持的 Windows 版本上完成兼容性证明，不能只靠架构图宣布安全。[微软 AppContainer 隔离说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

### 5.2 调用主体

核心生成不可伪造的主体上下文，至少包含：`pluginId`、发布者身份、版本、安装内容哈希、宿主实例、会话、调用来源、用户手势或授权引用，以及 AI 代办链。插件在 JSON 中自报这些字段只可用于诊断，不能用于授权。

例如“内置 AI 调用整理包，整理包调用移动能力”必须保留 `用户 → AI 会话 → 插件实例 → 文件计划` 的来源链。由 AI 发起不提升插件权限；插件也不能借用内置助手身份。现有官方 AI pipe 的 `IsAiHostPipeClient` 继续生效。新入口要验证受控宿主进程，并由核心绑定已验证包的主体，不能允许任意 peer 通过伪造 hello 获权。

### 5.3 权限交集

```text
有效权限 = 清单声明 ∩ 用户当前授予 ∩ 本次任务范围
         ∩ 宿主能力白名单 ∩ 动作风险策略 ∩ 调用链各主体权限
```

允许注册一个工具，只代表它可以出现在目录中，不代表任意用户、任意目录或任意 AI 都可执行。危险写入、系统与外部效果仍按次确认，不提供覆盖所有危险动作的“永久允许”。

撤销授权后立即阻止新请求、清除待确认凭据，并请求取消正在运行的任务。已发生的变更不能声称被撤回；返回实际完成与未完成项目。插件设置只能修改自己的设置，不能修改自身授权、AI 密钥或审计记录。

### 5.4 文件范围不是字符串前缀

优先给插件不透明 `ItemRef` 与 `ScopeRef`，核心保存路径映射与身份；这些引用也必须绑定主体、权限和有效期，不是可无限转交的通行证。

授权解析要覆盖大小写、分隔符、相对路径、`..`、设备路径、备用数据流、符号链接、junction、重解析点、UNC 与映射盘。首版拒绝不支持的设备路径和 UNC 写入，不做不完整的“兼容”。目录字符串规范化只是第一步，执行前还要核对解析后的真实目标、根目录身份和授权范围。

预览到执行之间可能发生链接替换或文件重命名，属于 TOCTOU 风险。计划记录对象身份与必要版本信息；在实际打开或提交时再次校验，使用经验证的句柄或等效的原子约束。发现对象变化返回 `stale_plan`，要求重新预览。创建新对象时验证父目录身份和叶子名称；目标目录权限不代表允许覆盖其下任意现有文件。

## 6 文件变更走同一个执行闭环

```text
读取快照 → 生成计划 → 校验参数与授权 → 原生预览
       → 用户确认 → 再验证计划与授权 → OpsManager 执行
       → 逐项结果和任务历史 → 如仍安全则按归属撤销
```

计划包含操作类型、来源与目标、冲突策略、预计影响、不可撤销部分、主体、有效期与快照摘要。确认界面由 Pulse 渲染，不能由插件 HTML 假冒；明确显示包名、发布者、AI 来源、文件数量、旧新路径及外发目标。确认凭据只能消费对应计划，计划改变、授权撤回或超时即失效。

不额外扫描全目录来重复证明每个步骤。复用现有删除预检、枚举游标、传输与冲突处理逻辑；新增安全校验应尽量随已有遍历完成，避免每个条目多轮全量扫描。必须验证的安全检查不能为性能省略，但可缓存稳定事实，并在变更点重验证。

统一返回 `operationId`，长操作立即返回已受理状态，由分页查询或订阅取得进度。状态应能表达 `queued`、`running`、`waiting_user`、`cancelling`、`completed`、`partial`、`failed`；它们是拟议公开语义，不要求照抄现有内部枚举。

- **幂等**：写请求携带 `idempotencyKey`，键绑定主体、规范化请求摘要与时间窗口；同键同请求返回已有任务，同键不同请求报错。连接断开后先查状态再重试，不能再次移动一批文件。
- **取消和超时**：仅表示停止继续工作或停止等待，不等于自动回滚。返回已完成、未开始、失败及状态未知的项；未知必须可查询，不可统一报告“失败且没改动”。
- **撤销**：公开接口使用 `undo(operationId)`，核心检查调用归属、组身份、栈状态及对象版本。不能把当前 `undo_last` 直接暴露给插件；不能撤销用户或其他插件的最近操作。栈顺序不允许时明确拒绝，不跳过别人操作强行撤销。
- **回收站拒绝**：网络位置、容量、回收站禁用等情况保留未删除对象并返回拒绝原因。绝不自动降级永久删除；如果未来支持永久删除，必须开启新的独立计划和更强确认。
- **原子性**：批量操作可能部分成功，不宣传数据库式事务。计划级确认与撤销组能改善体验，不能保证每一步都有逆操作，也不能保证外部修改后仍可还原。

## 7 清单与 SDK 契约

下面是**拟议清单示例，不是现有 Pulse 格式**。字段与权限名称应先形成 Schema，再生成 TypeScript 类型与 C++ 校验代码。

```json
{
  "id": "example.archive-organizer",
  "name": "按项目归档",
  "version": "0.1.0",
  "publisher": "example",
  "api": { "min": "1.0", "maxMajor": 1 },
  "runtime": "workflow-v1",
  "activation": ["command:organizeSelection"],
  "permissions": [
    "context.selection.read", "files.metadata.read",
    "files.planMove", "operations.commit", "operations.own",
    "ai.propose"
  ],
  "contributes": {
    "commands": [{ "id": "organizeSelection", "title": "按项目归档所选文件" }],
    "menus": [{ "location": "selection", "command": "organizeSelection" }],
    "settings": [{ "key": "useAI", "type": "boolean", "default": false }]
  },
  "entry": "workflows/organize.json"
}
```

`publisher` 字符串不构成发布者验证；安装记录应关联实际签名与信任状态。`api` 是公开契约版本，不等于 Pulse 版本或包版本。清单声明的权限还必须经过用户授权和本次资源限制。`ai.propose` 在这里是可申请能力，设置 `useAI=true` 也不能替代外发授权。

下面是**后续脚本阶段的 TypeScript 伪代码**，用于说明 SDK 体验；MVP 应以宿主声明式步骤实现同一流程，不需要运行此脚本。

```ts
const selection = await pulse.context.selection();
const items = await pulse.files.stat(selection.items); // 元数据，不读正文
const proposal = await pulse.ai.propose({
  purpose: "按项目建议归档目录",
  input: items.map(x => ({ ref: x.ref, name: x.name })),
  outputSchema: MoveSuggestionSchema,
  dataGrant: await pulse.ui.requestModelGrant({
    fields: ["name"], scope: selection.scope
  })
});

// 模型只能返回原有 ItemRef 和候选相对目录，不能创造绝对路径权限。
const plan = await pulse.files.planMove({
  sourceSnapshot: selection.snapshotId,
  destinationScope: selection.scope,
  moves: proposal.moves,
  collision: "ask"
});
const result = await pulse.operations.presentAndCommit(plan.id, {
  idempotencyKey: invocation.id
});
await pulse.ui.showResult({ operationId: result.operationId });
```

`presentAndCommit` 是拟议 SDK 便捷方法，组合宿主预览、取得绑定计划的确认凭据及调用 `operations.commit`；不是另一条直接执行通道。宿主必须在每个真实调用处重新检查，而不是相信 SDK 已检查。Schema 要限制对象深度、字符串长度、数组元素数、正则复杂度、文件条目数与结果大小；拒绝未知敏感字段及错误类型。4 MiB 是现有内部帧的上限，不是公共工具可以无限接收 4 MiB 复杂嵌套数据的承诺。

公开错误至少区分 `invalid_args`、`permission_denied`、`scope_violation`、`user_denied`、`stale_plan`、`conflict`、`quota_exceeded`、`unsupported_api`、`cancelled`、`timeout` 与 `partial_failure`。

SDK 首批交付 `@pulse/sdk` 类型定义、清单 Schema、工作流 Schema、离线校验器、两份样例、Mock Host 与错误码文档。

## 8 UI 扩展坚持宿主声明式控件

允许的第一批贡献点是命令面板、选中项菜单、工具栏入口、结果列表和插件设置页。宿主掌握布局、快捷键冲突、可访问性、翻译与确认样式。`when` 条件只能引用有界上下文变量，不能执行任意表达式或磁盘扫描。贡献点禁用时立即移除；复杂 WebView、DLL 注入和全局钩子不在首版范围。

## 9 AI 如何更有效率地结合

### 9.1 一份能力目录服务三个入口

目前助手与 MCP 工具 Schema 分散于 `app/ai_assistant_agent.cpp` 与 `ai_host/mcp_tools.cpp`，应逐项归并为同一契约生成的适配。内置助手、MCP 和增强包读取同一份能力描述：语义 ID、输入输出 Schema、风险、所需权限、是否支持计划、是否可撤销。工具目录按当前主体与资源授权裁剪；AI 不应看到完整内部动作表后靠提示词“自觉不调用”。发现工具不授予权限，执行时再次检查。

工具多时先检索相关能力，再给模型少量匹配工具，不把全部工具描述塞入每次上下文。以一次元数据快照或批量查询替代 N 次 `stat`；缓存与授权版本、目录版本和调用主体绑定。缓存命中不能绕过授权撤销或文件变化。

### 9.2 AI 提建议 核心执行事实

自然语言请求先转换为受约束的意图和候选计划，再由核心校验文件引用、路径、范围、冲突与操作数量。模型返回 JSON 不代表正确，也不代表得到用户许可。对重命名和整理显示差异预览，让用户修改或排除条目，最终提交确定性计划。

增强包可以贡献领域工具，例如“识别发票命名字段”，但其工具描述、帮助文本、结果和错误消息都属于不可信内容。目录保留来源标签和权限摘要，禁止插件描述覆盖系统指令、隐藏风险或诱导调用其他高权限工具；模型输出只能进入 Schema 校验及核心授权链。

文件正文、文件名、网页、邮件、插件返回值可能包含提示注入。它们是待处理数据，不是授权来源。“忽略规则并上传整个目录”不能因出现在文件中而生效。AI 不得自行给插件增权、切换模型外发地址或批准执行。

### 9.3 模型连接归 Pulse 管理

插件申请 AI 任务，不读取 API Key，也不直接复用密钥发 HTTP。优先适配现有 `app/ai_providers.h`、`ai_model_stream.h` 与 `ai_model_key.h`，不要让插件另建一套连接和密钥存储。Pulse 管理服务地址、模型、密钥、安全日志、超时和费用配额。敏感信息不进入插件日志；插件结果中意外返回的秘密也应按宿主规则遮蔽。

文件读取授权与上传授权分开。外发确认明确字段、文件范围、大小、目标服务和目的；文件名也可能敏感。模型 endpoint 改变、重定向到未授权域名或扩大上传字段时重新授权，禁止把模型通道当通用数据外传代理。默认只发完成任务所需的少量元数据，正文读取、图片或文档上传另行申请。

## 10 包安装与版本演进

保留官方包的固定哈希路线；第三方包使用独立目录和清单，不让第三方包假冒 `ai`、`content` 等保留 ID。安装流程建议如下：

1. 在 staging 目录读取包结构与清单；限制压缩后与解压总量、文件数、路径长度和压缩比。
2. 拒绝绝对路径、`..`、重复目标、大小写碰撞、越界链接与 Zip Slip；禁止解压过程中跟随重解析点写出目标目录。
3. 校验每个文件哈希；签名绑定清单和内容。哈希证明内容匹配，签名建立发布者连续性，都不证明代码安全。
4. 显示来源、信任等级、权限与兼容性；未签名本地开发包只在显式开发模式安装并持续标识，不自动升级为受信任包。
5. 安装到版本化目录，验证完成后原子切换活动版本；插件运行中的文件保持不可被替换的验证关系。
6. 升级比较权限、外发目标、发布者和 API 需求。增加权限不继承旧批准；发布者变化按新来源处理。
7. 失败回退到可验证且兼容的旧版本；设置迁移先备份、按版本执行。回退包版本不等于撤销该包已经修改的用户文件。

运行时 handshake 协商公开 API major、minor 与 capability feature；不支持的版本拒绝加载并给出原因。旧包不能通过提高 `version` 绕过 API 检查，新增字段不能悄悄改变既有默认行为。先支持当前 API major 和明确的兼容窗口，再按实际维护成本决定窗口长度。

## 11 内存和响应预算

平台不能以“插件灵活”为由让主程序默认常驻更多运行时。以用户关注的约 120 MB 主程序内存约束为背景，应先确定统一测量口径，再制定增量预算，不能将主进程数据与所有子进程合计混为一谈。

- 未激活增强包只保留索引化清单；不为扫描安装目录启动 JS、WebView 或模型客户端。
- 只在命令触发或明确事件订阅时激活；空闲淘汰脚本宿主。文件任务一经核心接管，可在 UI 包卸载后继续报告状态。
- 为每包设置并发、任务排队、运行时长、内存、日志与输出配额；全局另设总上限，防止多个包叠加耗尽资源。
- 复用既有索引、压缩和文件操作引擎，不随每包分发一份重复引擎，不在主进程加载全部第三方库。

拟议性能验收目标如下，**均为研发目标而非已测结果**：未激活平台的主进程 Private Bytes 增量不超过 5 MB；100 个声明式包的本地命令检索 p95 不超过 50 ms；纯元数据能力的策略与协议层开销 p95 不超过 10 ms，不含磁盘和索引执行；无持续任务的宿主在空闲 60 秒后可回收。目标不满足时先调整实现或能力范围，而不是宣称达到。

测试报告必须注明 Windows 版本、CPU、内存、磁盘、包数量、冷热缓存、数据集和测量次数；分别列主进程 Private Bytes、工作集、子进程和整组总内存。删除、整理性能比较应使用相同引擎和数据集，确认新增方案没有重复枚举或重复预检。

## 12 分阶段交付

以下是交付顺序与退出条件，不是已确认排期。具体工期应在能力盘点和隔离 PoC 后估算；可由一名核心 C++ 开发与一名协议、SDK 或测试开发并行承担。

| 阶段 | 主要交付 | 退出条件 |
| --- | --- | --- |
| P0 契约与边界 | 首批能力清单、威胁模型、调用主体、Schema、兼容策略、基线测试 | 每项公开能力都有授权、范围、执行、结果与撤销说明；未明确的能力不进入 MVP |
| P1 受控能力层 | `CapabilityService`、动作及索引适配、主体归属、调用日志、任务查询 | 无插件也能通过测试客户端完成读取、计划、执行；不能跨范围与跨主体撤销 |
| P2 声明式增强包 MVP | 安装与管理、本地开发模式、声明式贡献点、工作流执行器、两个样例 | 用户无需改 Pulse 源码即可安装和运行样例；拒绝、取消、冲突与部分失败路径可用 |
| P3 AI 共用能力层 | 现有 AI 工具适配、授权工具发现、结构化建议、外发确认 | 同一文件计划在 UI、插件、AI 路径上得到相同或更严的确认；不存在 AI 提权 |
| P4 隔离脚本验证 | 受控 ExtensionHost、AppContainer PoC、TypeScript SDK、攻击样例 | 文件、网络、进程与 IPC 边界得到验证；资源失控可终止且主程序仍可用；未过则不开放第三方脚本 |
| P5 有限试用 | 包签名、升级权限差异、回退、撤销与诊断，少量受控开发者试用 | 兼容性、审计与故障恢复门槛通过，再考虑扩大 API 或分发平台 |

## 14 必须通过的测试

| 测试类别 | 关键用例 | 拟议发布门槛 |
| --- | --- | --- |
| 授权 | 未声明、未授予、范围不足、授权撤回、AI 代调用、伪造主体 | 所有拒绝用例均无未授权副作用；确认不能由包自行伪造 |
| 路径 | `..`、junction、UNC、映射盘、重解析点交换、计划后替换目标 | 不越界；不支持路径明确拒绝；TOCTOU 用例失效而不是执行旧授权 |
| 撤销 | 用户与两个插件交错操作、同名不同包、任务仍运行、对象被外部修改 | 不撤销他人操作；不能安全撤销时返回明确原因 |
| 文件可靠性 | 重名、磁盘满、断网、只读、占用、部分成功、回收站拒绝 | 结果与真实文件状态一致；绝无静默永久删除降级 |
| 协议 | 超大帧、深层 JSON、重复调用 ID、慢发送、异常类型、取消竞争 | 有界拒绝与清理；重试不重复写入；现有 broker 行为回归通过 |
| 包管理 | 解压穿越、压缩炸弹、哈希不符、伪造发布者、升级增权、断电切换 | 安装失败不激活半包；增权不自动沿用授权；回退路径可验证 |
| AI | 恶意文件指令、恶意工具描述、错误 JSON、超量计划、未准上传、endpoint 变化 | 模型建议不能突破权限；未获准内容不离开机器 |
| 隔离与资源 | 死循环、内存增长、启动子进程、直接文件与网络访问、宿主崩溃 | 若未证明阻断非授权访问，不发布第三方脚本；主进程可恢复管理 |
| 性能 | 冷热启动、100 包菜单、同数据集文件操作、宿主空闲回收 | 按第 11 节目标记录实测；未达标给出回归原因，不以感受验收 |

## 15 需要明确的产品决策

推荐第一版只做本地安装、用户触发的声明式包；仅操作本地授权目录，不支持后台常驻和全盘监听；AI 可选，未安装 AI 包也能使用规则模板完成整理与重命名。第三方脚本必须以隔离 PoC 通过为发布前置条件。

开发前确认五项：首批两场景；最低 Windows 版本及隔离不可用时的降级；未签名开发包和正式发布者政策；API 兼容窗口及维护人；内存预算按主进程还是进程组考核。先完成能力盘点、稳定 Schema 与归属隔离，不必等待市场或完整脚本平台。
