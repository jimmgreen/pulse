# 文件操作多任务 · 第三阶段方案

日期：2026-11-24　分支：`perf/file-ops-opt-20261120`（第一、二阶段均未提交）

## 背景

用户在复制、移动、删除进行中会随手再开新的操作，不会去管“大任务”“小任务”。Pulse 不应拒绝，也不应在没有必要时让操作干等。整体分三阶段：

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| 一 | 主线程 + 3 条并行通道，按路径足迹准入；按盘调度（全局设备预算、机械硬盘轮转） | 已完成，未提交 |
| 二 | 任务中心界面：卡片下列出其他操作（进度、暂停/继续、取消），冲突不阻塞其他任务，显示等待原因，点选切换 | 已完成并实机验证，未提交 |
| 三 | 把“保守排队”缩到只剩真正必要的情况 | 本文 |

第一、二阶段的实测结果：

- 跨盘两任务同时进行用时 57.4 s，依次进行用时 73.8 s。
- 同一机械硬盘两任务同时进行用时 118–124 s，依次进行中位数为 113.5 s；其中小任务在 64–74 s 先完成。
- 并行通道浸泡 200 轮：0 失败，内存约 11.3 MB，句柄 160。
- 实机测试：4 个复制同时运行；列表里的暂停、继续、取消、点选，“需要你选择”，以及两种等待原因都工作正常。

## 现在还会排队的情况

调度器（`src/ops/ops_manager_interactive.inl` 的 `InteractiveThread`）只在能证明安全时才让操作进并行通道。证明不了就排队，这是正确的默认值，但有不少情况是“证明不了”，而不是“确实冲突”：

| # | 情况 | 代码位置 / 拒绝码 | 性质 |
| --- | --- | --- | --- |
| 1 | 两个操作的名字足迹重叠（同一目标、父子目录、同一源） | `InteractiveRequestsConflict`，拒绝码 1 / 8 | **两个只读源也算重叠**：实测中 `video_1→dst4` 要等暂停中的 `video_1→dst2`，原因只是两者读同一个文件 |
| 2 | 源、目标或其任一上级目录是重解析点（junction、符号链接、挂载点） | `InteractivePlainPath`，拒绝码 2 | 保守：链接指向哪里本可以解析出来 |
| 3 | 目标树里有链接，或 250 ms 内没遍历完 | `InteractiveTargetTreeKnown`，拒绝码 16 / 32 / 64 | 保守：大目标树或慢盘上经常超时 |
| 4 | 网络共享、映射网络盘（非 `DRIVE_FIXED`/`DRIVE_REMOVABLE`） | `InteractivePlainPath` | 保守：同一共享可能有多个名字，无法只凭名字证明 |
| 5 | 名字有别名风险：短名 `~`、`/`、尾随点或空格、`:`（ADS） | `InteractivePlainPath` | 必要性低：可以先规范化再比较 |
| 6 | 主线程正在跑一个“非普通”请求（网络、链接等） | 拒绝码 4 | **最伤体验**：一个网络复制会让后面所有操作都排队 |
| 7 | 源超过 20000 项 | `kMaxLaneSources` | 只是成本控制 |
| 8 | 请求形状不在并行范围内：手机/Shell 传输、撤销/重做、受控任务、锁定重试、`close_first`、批量重命名、模板超过 1 MB、特殊冲突策略 | `InteractiveRequestShape` | 部分必要；且撤销或受控任务排在队首时，调度器整个停下（“these keep their place”） |
| 9 | 同时进行的操作已满（主线程 + 3 条通道） | `kLaneCount = 3` | 必要的资源上限 |

另外两个和调度相关的遗留问题：

- 删除没有接入机械硬盘轮转（`SpindleGate`）。同一块机械硬盘上，删除和复制同时进行时会互相抢磁头。
- 同一机械硬盘上，两个任务同时进行仍比依次进行慢约 5–9%。轮转之后差距已经缩小，但没有消除。

## 第三阶段目标

用户看到的“排队中”，只应剩下面三种原因：

1. 两个操作确实要写同一个实际文件或目录（或一个写、一个读）。
2. 同时进行的操作已满。
3. 同一块机械硬盘上同时进行会更慢，所以改为轮流（新的等待原因，见 3.6）。

## 方案

### 3.1 按实际身份比较，不再只比名字

- **足迹记录实际位置：** 对每个源、目标父目录，打开句柄（`FILE_FLAG_BACKUP_SEMANTICS`，不跟随最后一级链接时加 `FILE_FLAG_OPEN_REPARSE_POINT`），用 `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` 得到卷 GUID 加规范路径。足迹同时记录原始名字和解析后的位置，比较时两者都要比。
- **链接改为纳入足迹：**
  - 源或上级目录是 junction 或符号链接：解析后的目标位置加入足迹，不再拒绝。
  - 目标树中遇到链接：把链接指向的位置加入足迹，继续遍历，不再整单拒绝（对应拒绝码 16 / 32 / 64）。
  - 解析失败，或链接指向网络位置：维持现状，排队。
- **短名、尾随点、`/`：** 规范化后再比较（短名用 `GetLongPathNameW`）。ADS（`:`）维持排队。
- **代价控制：** 解析在调度线程上进行，沿用 `InteractiveTreeWalkBudget` 的截止时间和被取代时中断的机制。解析结果只在一次准入内有效，不跨准入缓存，和现在 `InteractivePathProof` 的规则一致。

### 3.2 读和写分开

- 足迹的每一项带上角色：
  - 复制的源 = 读；
  - 移动的源 = 写（会删除）；
  - 删除 = 写；
  - 所有目标 = 写；
  - 回收站 `X:\$Recycle.Bin` = 写。
- 只有两个“读”重叠时不算冲突；读和写、写和写重叠仍然排队。
- 能直接解决实测中“两个复制读同一个文件也要排队”的问题。

### 3.3 主线程的非普通操作不再挡住所有人（拒绝码 4）

- 为非普通请求算一个“可能触及范围”：
  - 网络路径 → 该服务器；
  - 链接无法解析 → 整个卷；
  - 形状未知 → 所有本地卷，即维持现状。
- 候选操作只在和这个范围相交时排队。例如在复制到 `\\nas\share` 的同时，删除 `D:\tmp` 不必再等。

### 3.4 网络位置（保守放开）

- 映射盘先用 `WNetGetUniversalNameW` 还原成 UNC。
- 规则：
  - 不同服务器之间：允许并行；
  - 同一服务器上：任意两个写操作仍然排队，因为 DFS 和同一目录多个共享名都可能是别名；
  - 同一服务器上只读 + 写、且路径不重叠：可以并行。
- 网络操作不进机械硬盘轮转，但要受全局设备预算约束。
- 网络中断时，冲突、失败的处理和现在的主线程一致。

### 3.5 撤销和受控任务不再冻结调度

- 现在：队首是撤销或受控任务时，后面的操作全部不评估。
- 改为：它们留在原位不并行，但调度器可以越过它们评估后面的操作。条件是后面的操作和它们的足迹不重叠，撤销的足迹按它要恢复的路径计算。
- 撤销 / 重做之间的相对顺序保持不变。

### 3.6 机械硬盘：删除接入轮转，同盘可选择轮流

- `DeleteNativeParallel` 在机械硬盘上接入 `SpindleTurn`：以每批（目录）为单位取得和交还轮次。
- 新增等待原因“同一块机械硬盘，轮流进行”（`OpWaitReason::SameDisk`）。
- 两个大任务（预估都超过数 GB）落在同一块机械硬盘上时，后来的那个直接排队，而不是同时运行。小任务仍然插进轮转里，保住“小任务先完成”的体验。
- 阈值要按实测选定；需要同时比较“总用时”和“小任务完成时间”，不能只看其中一项。

### 3.7 第二阶段遗留的界面问题

- 排队中的操作也能暂停（`QueueItem::transfer_paused` 已有），列表里给排队行加上暂停按钮。
- 超过 4 行时，“另有 N 项操作”要能点开，列出全部任务（含等待原因）。
- 第一阶段的右键“正在进行的操作”菜单和新的列表功能重复，决定是否删除。
- 等待原因随新增情况补全，例如“链接指向的位置正在使用”“同一网络位置”。文字只改 `tools/l10n/catalog.tsv`。

## 必须保持的安全不变量

1. 任何时刻，两个操作不能同时写同一个实际文件或目录（按解析后的身份，不只按名字）。
2. 一个操作在写的位置，另一个操作不能同时读或删除。
3. 撤销 / 重做的先后顺序不变；部分失败的重试仍然是独立任务。
4. 解析不了的一律回到排队，不猜测。
5. 冲突对话框按任务弹出，回答只作用于对应任务（现有 token 路由不变）。
6. 调度线程上的文件系统访问都有截止时间，界面线程不做任何解析。

## 建议顺序

每一批完成并通过相关验证后再做下一批：

1. 3.2 读写分开：改动小，直接解决实测中看到的问题。
2. 3.1 按实际身份比较（链接纳入足迹）：收益最大，也是安全风险最高的一步，测试要最完整。
3. 3.3 非普通操作不再挡住所有人。
4. 3.6 删除接入轮转，以及同盘轮流的等待原因（需要性能对照）。
5. 3.5 撤销和受控任务不再冻结调度。
6. 3.4 网络位置。
7. 3.7 界面遗留问题，可以穿插在前面各批之间做。

## 风险

- **别名漏判是数据安全问题：** 漏判会导致两个操作同时写同一个文件。所以 3.1 解析不了时必须回到排队，测试要覆盖“同一目录的两个名字”。
- **调度线程负担加重：** 解析会增加调度线程的开销。大批量粘贴时，要确认准入耗时（`ops_interactive_admission` 事件里的 `walk_ms`）不会明显变长。
- **同盘轮流需要取舍：** 同一块机械硬盘上，“总用时”和“小任务先完成”此消彼长，阈值需要实测，不能拍脑袋。
