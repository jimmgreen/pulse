# Pulse 原生增强包：审查结论与执行计划

更新日期：2026-11-08。**本文件是唯一主路线图。** 旧版全文在 [archive/native-platform-roadmap-20261106.md](archive/native-platform-roadmap-20261106.md)。

## 0. 执行规则（每轮都适用）

1. **先有用例，再有接口。** 新的公开 API 必须由 `sdk/native/samples/` 里某个参考插件的真实需求驱动。当前的驱动插件是**压缩包插件**（第 3 节）；它用不到的字段、版本和贡献点都不加。
2. **1.0 之前不追加版本号。** 接口可以直接修改，同时把 `PULSE_SDK_PREVIEW` 加一，宿主拒绝预览号不匹配的插件。不再出现 `fileops` V1→V4 这种“末尾追加函数表”的兼容层。**1.0 之后**才承诺 ABI 稳定，规则见 P3.2。
3. **验收要轻、要真：** 构建受影响的目标，运行一个定向测试，跑通对应参考插件；只有新增 UI 表面时才附一张应用内截图。不再为每项能力写 `N PASS / 0 FAIL` 的 report.json、成套截图和隔离宿主报告。
4. **信任模型说实话。** 插件面向外部作者，但原生 DLL 和 Pulse 在同一进程，拥有整个进程的权限，任何宿主侧检查都挡不住恶意代码。所以：
   - **要做**：签名或哈希验证、发布者身份、安装时向用户展示插件声明的能力、用户明确启用、崩溃后自动停用、破坏性文件操作的审计记录（出问题时能查到是哪个插件做的）。
   - **不做**：每次调用都检查主体或权限，以及任何对外声称“插件被隔离、被限制”的设计或文案。
5. **测试代码不进 `pulse.exe`。** 探针（`*_probe.cpp`）只能放进测试目标，或者放在 `PULSE_WITH_TEST_HOOKS` 后面，且发布构建必须关掉这个选项。
6. **文档只留 4 份：** 本路线图、`sdk/native/README.md`（接口参考）、`docs/extensions-sdk-quickstart.md`（上手）、`docs/native-packages.md`（打包与签名）。新信息写进这 4 份，不另开文件。外部作者能看到的只有后三份，必须能独立读懂。
7. 遵守仓库 `AGENTS.md`：只构建受影响的目标，UI 文字走 `catalog.tsv`，阻塞操作不进 UI 线程。

## 1. 结论：可行吗

**核心路线可行，而且选得对；推进慢的原因在流程和范围，不在技术。**

- 可行的部分：同进程 C++ DLL、C ABI 用 `query_interface` 加 `size`/`version` 协商接口表、宿主负责绘制而插件只组合控件和数据、只在 UI 线程调用加 `pulse.dispatch` 回投——这是 Notepad++、foobar2000、OBS 这类成熟插件体系的做法。现有的 `abi.h`、`ui.h`、`ui_mount.h`、`dispatch.h` 设计干净，可以继续用。
- **桌面磁贴是下一阶段的目标，前提是插件系统先完善**（第 7 节）。它涉及桌面层级、Explorer 重启、多显示器等独立风险，所以先由压缩包插件把通用能力做扎实，再开始做它。可以提前做一次短的技术验证，摸清它需要宿主提供什么，但不提前设计桌面接口。

## 2. 为什么推进慢（审查发现）

以下依据 2026-11-07 对仓库的静态审查：读了文档、SDK 头文件、目录结构和 CMake。**没有构建，也没有运行测试。**

| 问题 | 证据 | 影响 |
|---|---|---|
| **每项能力的仪式成本过高** | 一项能力要同时改：公开头、宿主适配器、`api-catalog.json`（70 KB）、`api_description.generated.h`（500 KB）、`ui-model.schema.json`（118 KB）、`manifest_schema.generated.h`（131 KB）、TS 声明、作者文档、MCP、独立样例 DLL、隔离真实宿主验收报告和截图 | 一个小接口要花几轮；大部分时间不在功能本身 |
| **信任设计放错了地方** | 按调用主体逐次做权限检查和审计，但同进程 DLL 能绕过所有这些检查（文档自己也承认“不构成原生代码沙箱”）；而外部作者真正需要的多文件包、签名发布流程、崩溃自动停用都还没有 | 成本花在挡不住风险的地方，真正的风险没人管 |
| **预览期就在做兼容版本** | `fileops` 几天内从 V1 演进到 V4，每版都“保留前缀、末尾追加”，还要逐版同步清单和 schema | 还没有任何外部用户，却已经在背兼容包袱 |
| **两套 UI API，且泄漏宿主内部** | `pulse.ui`（7 类节点）和 `pulse.ui.model`（41 类）并存；后者包含 `TITLE_BAR_BUTTON`、`STATUS_BAR`、`PANE_HEADER`、`STAGING_TRAY`、`DRIVE_ITEM`、`FILE_ROW` 等宿主外壳控件 | 一旦开放给外部作者，宿主就再也不能自由改自己的 UI |
| **声明式时代的残留代码** | `src/app/extensions/` 约 150 个文件，其中 `runtime`、`palette`、`toolbar_contributions`、`workflow_*`、`resource_*`、`transfer_*`（JSON broker）属于旧路线；原生路线只在 `native/` 子目录 | 两条路线互相牵连，每次改动都要考虑旧路径 |
| **约 25 个探针编进 `pulse.exe`** | `src/app/extensions/*_probe.cpp` 和 `native/*_probe.cpp` 被 `GLOB_RECURSE PULSE_APP_SOURCES` 收进主程序；发布构建关掉测试钩子时，排除规则里也没有它们 | 发布的程序里带着测试代码 |
| **文档过载拖慢 AI** | `docs/extensions-*.md` 约 30 份、合计约 220 KB，加上 SDK 文档；单是 `extensions-sdk.md` 和 `extensions-capability-inventory.md` 就各约 73 KB | 每轮接手的 AI 要先吞下大量文字，上下文被占满，产出变慢、变保守 |
| **接口不是由真实插件拉动的** | 文件服务按“开放能力清单”逐项补（永久删除、缩略图、标签……），而不是按某个插件需要什么来补 | 做了很多，日常能用的插件仍然很少 |
| **没有崩溃保护** | `native/module.cpp` 用 `LoadLibraryExW` 加载并直接调用插件；没有崩溃归因，也没有“上次启动时崩溃就自动停用” | 对外部作者的插件来说，这是最先会遇到的问题 |

## 3. 目标和参考插件

**作者：外部开发者**（也包括你自己和 AI）。1.0 的完成标准：

> 外部开发者只拿到 SDK 压缩包（头文件、样例、quickstart、MCP），就能写出、签名、打包、发布一个和压缩包插件同等复杂度的插件；用户能安装、启用、更新、停用、移除它，崩溃时 Pulse 能自动恢复并指出是哪个插件。

**参考插件按顺序：**

1. **压缩包插件（主驱动，现在开始）**：把现在宿主里的“解压缩增强包”拆出去，做成一个完整插件。它需要的能力几乎覆盖了文件管理器插件的全部形态：
   - 多文件包：插件 DLL 加 `7z.dll` 和许可证文件；
   - 预览提供者：7z、rar 等格式的内容树；
   - 右键命令：“解压到此处”“解压到…”“添加到压缩包…”；
   - 插件自己的长任务：进度、取消、在状态栏胶囊和操作窗口里显示；
   - 写入文件：走宿主的冲突处理和撤销；
   - 设置页。
2. **目录工作台**（已有 `directory-workbench`）：侧栏和工作区挂载、分页数据，继续当回归样例。
3. **桌面磁贴（下一阶段）**：插件系统通过 1.0 预览发布后开始，见第 7 节。

**压缩包插件的现状**（审查所见）：宿主通过 `pack_catalog_generated.h` 的 `kArchivePackRelease` 下载 `7z.exe` 和 `7z.dll`；`src/preview_host/archive_pack.cpp` 在受限的子进程里运行 `7z.exe l`，只为预览生成内容列表（7z、rar、zipx、分卷 .001 等），**不做解压**。树形预览由 `src/ui/archive_preview.cpp` 绘制。zip 的读取（`zip_entry.cpp`）和压缩（`zip_compress.cpp`，用系统自带的 libarchive）是宿主内置功能，**不随插件拆走**。

## 5. 架构要点

- **线程**：除 `dispatch.post/cancel` 和后面新增的任务进度上报外，所有调用和回调都在宿主 UI 线程。插件的耗时工作放在自己的线程里，结果用 `dispatch` 回投。
- **寿命**：停用的顺序是：阻止新调用 → 注销 UI、命令和提供者 → 取消任务 → 等待在途回调 → `destroy`（插件在这一步结束自己的线程）→ `FreeLibrary`。不支持热替换，升级在重启后生效。
- **内存**：跨边界只传 `PulseStringView`、句柄和固定宽度结构。双方都不释放对方分配的内存，异常不得跨越边界。
- **文件写入**：插件不直接写用户的目标目录。插件先把产物写到宿主分配的**暂存目录**（与目标同卷，放在隐藏位置），再交给宿主执行“暂存 → 目标”的提交。冲突处理、确认、撤销、刷新和到达后选中都复用宿主现有的路径。同卷时提交只是重命名，代价很小。
- **崩溃**：同进程插件崩溃时，宿主无法继续运行。宿主要做到的是：能归因到具体插件、下次启动自动停用、提示用户。进程外插件宿主可以作为 1.0 之后的选项，现在不做。
- **性能底线**：没有启用插件时，Pulse 的启动和内存不变；插件按需加载。

## 7. 桌面磁贴（下一阶段，前提是 P1 和 P3.1 完成）

用户体验和分工保持旧版第 6 节的设想：插件按自己的规则整理桌面文档，以磁贴和分组呈现；“整理展示”默认只改布局，移动、重命名、删除真实文件是独立操作，走宿主流程；停用或退出后桌面完全恢复。

**插件系统需要先具备的能力：**

| 需要的能力 | 由谁提供 |
|---|---|
| 桌面文件夹（用户的和公共的）快照与变化监听 | 已有 `pulse.directories`，补上“已知文件夹”的定位 |
| 图标和缩略图 | P2 |
| 打开、右键命令、拖入拖出 | P1.2，外加拖放接口（待设计） |
| 插件自有布局的持久化 | 已有 settings |
| 桌面承载面：窗口进入桌面层、多显示器和 DPI、焦点、Explorer 重启恢复、退出还原 | 新接口，**由技术验证的结论决定怎么做** |

**技术验证（可以提前做，2–3 天，限定时间）**：写一个独立的小 exe（不是 Pulse 插件），把窗口挂到桌面层（WorkerW / Progman），验证以下几点：

- Explorer 重启后能恢复；
- Win+D 和“显示桌面”时的表现；
- 多显示器、不同 DPI、显示器热插拔；
- 有全屏应用时的层级；
- 和桌面图标之间的命中、拖放；
- 退出后完全还原，不留下拦截窗口。

把结论写回本节。它决定承载面是宿主接口、插件自己调 Win32，还是单独一个承载进程。**在 P1 完成前不实现桌面承载接口。**

## 9. 已确定的决定（2026-11-07，维护者）

1. **面向外部作者。** 1.0 后承诺 ABI 稳定；信任靠签名、发布者身份和崩溃自动停用，不靠宿主侧的权限检查。
2. **桌面磁贴是下一阶段方案**，前提是插件系统先完善；它驱动第 7 节的能力，但不阻塞 P0 到 P3。
3. **不要声明式 JSON 命令**，由原生命令贡献替代（P0.6、P1.2）。
4. **把“解压缩增强包”拆出去**，作为主参考插件来完善（第 3 节、P1）。

### P1.6 设置页实施状态

`pulse.settings.pages` V1 提供每实例一页的原生 UI-model 设置页，专用 query 复用 pulse.ui.model / pulse.ui.events，不与引擎面板共享挂载。归档样例提供默认解压目录（空值使用归档目录）、宿主目录浏览、压缩格式/级别及加载/保存/错误状态。保存使用现有resources版本CAS，冲突后保留草稿并刷新版本，用户明确重试才写入。extract-to初始目录采用已保存值，extract-here含义不变。P1.6 的真实宿主安装、升级、回退三轮已验收页面挂载、窄布局、重启保留与冲突；P1.8 统一 UI 接口后再次通过设置页验收。证据及边界见第 5 节，压缩创建已在 P1.10 完成本地路径范围验收。

### P1.10 验收边界与复现（2026-11-08）

- 复现：`python tools/extensions/test_native_compression.py --pulse build-extensions/p0-host/pulse.exe --sample-build build-extensions/p16-settings-sample --output <新的隔离目录>`。宿主须启用 `PULSE_WITH_TEST_HOOKS`，普通发布构建不能运行此探针。
- 证据：`build-extensions/p110-compression-acceptance-04/profile/capture/report.txt` 及同目录三张应用内截图。首次使用关闭探针的宿主未产生报告；后续发现并修复本地扩展路径被误拒绝，失败记录保留在 acceptance-01 至 03。
- writer 接受本地绝对路径及 `\\?\C:\…`；不支持 UNC、重解析点、硬链接。最多256个来源、4096个成员、64层、总输入4 GiB。单选采用原名加格式后缀，多选使用 Archive；同名由宿主冲突流程处理。
- 7z需要可定位输出流回填文件头，已实现 Seek/SetSize；不能以 ZIP 写入成功推断 7z 正确。10项 writer 检查只覆盖记录中的边界，不代表网络路径或全部极限规模通过。
